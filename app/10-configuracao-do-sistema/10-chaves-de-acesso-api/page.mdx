# Chaves de Acesso API

A aba **Chaves de Acesso API** permite criar tokens para integrações externas que consomem a API do Ducke CRM em nome da operação. Novas chaves usam o prefixo `ducke_` (ex.: `ducke_a1b2…`).

<img src="/prints/setup-user-tokens.png" alt="Tela de chaves de acesso API no setup" style={{ borderRadius: '0.5rem' }} />

## Como acessar

1. Abra **Configuração** no menu.
2. Selecione a aba **Chaves de Acesso API**.

## Criar uma chave

1. Clique em **Adicionar Chaves de Acesso API** (botão no topo).
2. Informe um **nome** descritivo (ex.: *Integração ERP*, *Webhook interno*).
3. Confirme — o token completo (com prefixo `ducke_`) é exibido **uma única vez**.
4. Use **Copiar** no diálogo, guarde em local seguro e confirme **Já copiei**.

<Callout type="warning">
  Trate cada chave como senha. Depois de fechar o diálogo, o secret completo não pode ser recuperado. Se perder a chave, exclua-a e crie outra. Não compartilhe em chats públicos nem commite em repositórios.
</Callout>

## Gerenciar chaves existentes

A tabela lista **Nome**, preview mascarado da **Chave de Acesso** (início e fim, ex.: `ducke_abcd…wxyz`) e **Ações**:

- **Editar:** altera o nome identificador.
- **Excluir:** revoga o acesso imediatamente.

Não há botão para copiar o secret completo a partir da lista — apenas o preview.

## Quando usar

- Automações que criam ou atualizam leads via API.
- Integrações com ERP, BI ou ferramentas internas.
- Scripts de migração ou sincronização sob demanda.

## Ferramenta MCP e API

Cada ação existe em par: a ferramenta MCP (para assistentes de IA que falam o protocolo MCP) e a API fazem a mesma coisa e devolvem os mesmos dados. As duas usam a mesma chave de acesso e só enxergam as origens que o usuário da chave pode ver.

Para conectar a ferramenta MCP, configure no seu assistente um servidor MCP do tipo HTTP com:

- **Endereço:** o mesmo endereço da API que sua integração já usa, no caminho `/mcp`.
- **Cabeçalho:** `Authorization: Bearer ducke_…` (a sua chave de acesso).

| O que fazer | Ferramenta MCP | API |
|---|---|---|
| Listar as origens e os estágios de cada uma | `list_origins` | `GET /api/v2/origins` |
| Listar os cards de um estágio da origem, uma página por vez | `list_stage_leads` com `originId`, `stageId` e `page` | `GET /api/v2/leads?originId=…&stageId=…&page=…` |
| Criar um card | `create_lead` | `POST /api/v2/leads` |
| Mover um card para outro estágio da origem (e, se quiser, trocar o responsável junto) | `move_lead` com `leadId`, `stageId` e `userIds` opcional | `POST /api/v2/leads/:id` com `stageId` (e `userIds`) |
| Trocar o responsável sem mover o card | `set_lead_users` com `leadId` e `userIds` | `POST /api/v2/leads/:id` com `userIds` |
| Reescrever as anotações | `set_lead_description` com `leadId` e `description` | `POST /api/v2/leads/:id` com `description` |
| Copiar um card para outra origem | `copy_lead` com `leadId`, `originId`, `stageId` e, se quiser, `userIds` e `copyContacts` | `POST /api/v2/leads/copy` com `leads: [id]`, `originId`, `stageId` (e `userIds`, `copyContacts`) |
| Listar as etiquetas, com busca pelo nome | `list_tags` com `search` opcional | `GET /api/v2/tags?search=…` |
| Adicionar uma etiqueta a um card | `add_lead_tag` com `leadId` e `tagId` | `POST /api/v2/leads/:leadId/tags/:tagId` |
| Remover uma etiqueta de um card | `remove_lead_tag` com `leadId` e `tagId` | `DELETE /api/v2/leads/:leadId/tags/:tagId` |
| Colocar etiquetas pelo nome num card | `add_lead_tags_by_name` com `leadId` e `tagNames` | `POST /api/v2/leads/:leadId/tags` com `tagNames` |

Para ler um estágio inteiro, comece na página `1` e peça a próxima até a lista vir vazia: aí o estágio acabou. Cada página traz até 100 cards, na ordem do quadro, e cada card aparece uma vez só. Um estágio que não é da origem informada dá erro (`Stage not found`), em vez de uma página vazia.

### O que cada card da lista traz

A ferramenta MCP e a API devolvem os mesmos dados de cada card, então a lista basta para decidir se vai copiar, mover, etiquetar ou mandar mensagem, sem abrir o card de novo:

| Dado | Campo |
|---|---|
| Qual card é | `id` e `name` |
| Em qual estágio da origem está | `stageId` e `stage` (com o nome do estágio), `originId` e `origin` |
| Documento | `tin`, sem pontuação |
| Anotações, exatamente como foram salvas | `description` |
| Etiquetas, com os nomes dados | `tags` (cada uma com `id` e `name`) |
| Pessoas do card | `contacts` (cada uma com `name`, `phoneNumber` e `email`) |
| Responsável | `users` (cada um com `id`, `username` e `email`) |

As anotações voltam caractere por caractere como foram gravadas, ao criar o card ou ao reescrevê-las, inclusive espaços, quebras de linha e acentos: uma marca que você deixa ali para ler depois volta igual. O documento é o jeito de conferir se a empresa já existe na origem antes de criar ou copiar um card.

### Criar, mover, trocar o responsável e reescrever as anotações

- **Criar um card** aceita o nome, a origem e o estágio onde ele entra (`name`, `originId`, `stageId`), as anotações (`description`, gravadas exatamente como enviadas), o documento (`tin`, sem pontuação ao salvar), `city`, `state`, `country`, as etiquetas pelo nome (`tagNames`; uma etiqueta que ainda não existe é criada com o nome enviado), os responsáveis (`userIds`) e as pessoas do card (`contacts`, cada uma com `name`, `phoneNumber` e `email`).
- **Mover** sem informar `userIds` mantém o responsável atual. Com `userIds`, o card muda de estágio e de responsável no mesmo passo.
- **Trocar o responsável:** a lista nova substitui a antiga, e uma lista vazia deixa o card sem responsável. O card continua no mesmo estágio.
- **Reescrever as anotações:** o texto novo substitui o antigo, exatamente como foi enviado (não acrescenta uma linha no final). O estágio e o responsável não mudam.

Os ids dos responsáveis são os do campo `users` de cada card na lista. Ao mover ou trocar o responsável, só valem o usuário da chave e as pessoas abaixo dele na hierarquia; um id fora disso, ou de quem não é da empresa, dá erro (`One or more user ids are invalid for this tenant`) e nada muda.

### Copiar um card para outra origem

- A cópia cria um card novo no estágio escolhido (`originId` e `stageId` de uma origem que o usuário da chave pode ver), com o nome, o documento, as anotações, a cidade, o estado, o país e as etiquetas do original. O card original continua na sua origem, sem mudança.
- **As pessoas do card vão junto** (nome, telefone e e-mail). Para copiar sem elas, envie `copyContacts: false`.
- **Responsável:** sem `userIds` (ou com uma lista vazia), o card novo fica sem responsável. Com `userIds`, ele fica só com essas pessoas, que precisam ser da empresa e ter acesso à origem de destino; senão dá erro e nada é copiado.
- **A cópia não procura duplicado** e nunca junta dois cards: mesmo que a origem de destino já tenha um card com o mesmo documento, a cópia cria outro card. Se você não quer o card repetido, confira o documento na lista do estágio antes de copiar.
- Um card que veio da Prospecção também pode ser copiado; o vínculo com o resultado da prospecção fica só no original.
- A resposta é `{ "success": true, "message": "Leads copiados com sucesso" }`. Um card que o usuário da chave não enxerga dá `Lead not found`, uma origem que ele não acessa dá `Origin not found` e um estágio de outra origem dá `Stage not found`.

### Etiquetas

- **Listar etiquetas** mostra as etiquetas usadas nos cards das origens que o usuário da chave pode ver, em ordem alfabética. A busca (`search`) acha parte do nome, sem diferenciar maiúsculas de minúsculas.
- **Adicionar** e **remover** mexem numa etiqueta por vez, pelo id (`tagId`, da lista de etiquetas ou do campo `tags` do card). As outras etiquetas do card ficam como estão.
- **Colocar etiquetas pelo nome** acrescenta ao card só os nomes enviados: uma etiqueta que ainda não existe é criada, uma que o card já tem não dá erro nem aparece duas vezes, e as outras etiquetas do card ficam. Não é preciso mandar a lista inteira. O nome é comparado sem diferenciar maiúsculas, então `cliente` usa a etiqueta `Cliente` que já existe.
- Cada nome de etiqueta tem até 30 caracteres. Um nome maior dá erro (`Tag name must be at most 30 characters`) e nada é criado, nem ao criar o card.
- As respostas de adicionar, remover e colocar pelo nome trazem as etiquetas do card (`tags`). Um card que o usuário da chave não enxerga dá `Lead not found`, e uma etiqueta de outra empresa dá `Tag not found`.

### Chamadas demais de uma vez

A ferramenta MCP e a API dividem um limite de **60 chamadas por minuto** por endereço IP de quem chama. Quando você passa dele, por exemplo ao atualizar muitos cards seguidos, a chamada é recusada antes de fazer qualquer coisa:

- **O card fica onde está.** Nada muda: nem o estágio, nem o responsável, nem as anotações, nem as etiquetas, e nenhuma cópia é criada.
- **Não é uma falha do card.** A resposta tem `code: "RATE_LIMITED"` e pede para ir mais devagar. Não mande o card para um estágio de erro: espere e mande a mesma chamada de novo.
- **Quando tentar de novo:** `retryAfter` diz em quantos segundos.

| Onde | Como a recusa chega |
|---|---|
| API | Status `429`, cabeçalho `Retry-After` e o corpo `{ "error": "Too many requests: slow down and send it again in 30 seconds. Nothing was changed.", "code": "RATE_LIMITED", "retryAfter": 30 }` |
| Ferramenta MCP | Resultado da ferramenta com `isError: true` e, no texto, o mesmo corpo da API. Outras chamadas do protocolo (como `tools/list`) recebem `429` com um erro JSON-RPC que traz esse corpo em `data` |

As chamadas pela ferramenta MCP e pela API contam juntas: gastar o limite numa delas também segura a outra até o tempo de `retryAfter` passar. Os outros erros (`Lead not found`, `Stage not found`…) continuam com a mensagem deles e nunca trazem `RATE_LIMITED`.

## Segurança

- Revogue chaves não utilizadas.
- Crie uma chave por integração para facilitar auditoria.
- Restrinja quem tem permissão de escrita nesta aba.
